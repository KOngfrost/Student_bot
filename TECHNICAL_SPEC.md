# Техническое задание: единый бот-помощник для студентов

## 1. Цель проекта

Создать многофункционального VK-бота-помощника для студентов с логикой обработки обращений, разделением по отделам и административным управлением.

Основная задача — обеспечить:

- вход для студентов через VK;
- маршрутизацию обращений по отделам;
- наличие статусов и истории заявок;
- административную работу внутри бота;
- веб-управление для суперадмина;
- ежедневную отчётность в Excel и отправку по email.

---

## 2. Анализ текущего состояния проекта

На текущий момент в проекте уже имеется базовый каркас:

- VK-бот на базе `vkbottle`;
- общая модель данных через SQLAlchemy;
- базовые сущности: `users`, `admins`, `departments`, `tickets`;
- стартовое меню, показывающее разделы и кнопку `Мои заявки` при наличии активных обращений;
- точка запуска через общий `main.py`.

### Что уже реализовано

- создание/запрос пользователя по `vk_id`;
- определение статуса администратора;
- отображение главного меню в VK;
- заготовка структуры моделей для заявок и отделов.

### Что ещё не реализовано

- полноценная анкета Жилбыт и Корпоративного отдела;
- создание и хранение заявок из пользовательских сценариев;
- админ-меню для обработки заявок;
- FAQ-дерево для Информ;
- регистратура на мероприятия и подписки Культмасс;
- анонимное обращение;
- веб-админка и отчётность.

### Вывод по анализу

Проект находится на начальном этапе MVP. Текущее состояние соответствует только общему архитектурному каркасу и базовой модели данных, но не покрывает бизнес-логику, описанную в исходном ТЗ.

---

## 3. Общее описание решения

Система состоит из следующих слоёв:

1. Клиентский слой
   - VK-бот.

2. Бизнес-логика
   - общий ядро `BotCore`;
   - обработчики сценариев отделов;
   - маршрутизация заявок;
   - статусная логика;
   - логика FAQ и событий.

3. Данные и хранение
   - PostgreSQL;
   - SQLAlchemy Async;
   - Alembic для миграций.

4. Административный слой
   - внутреннее меню администратора в боте;
   - веб-панель суперадмина.

5. Отчётность
   - генерация Excel-отчётов;
   - отправка по email;
   - при необходимости — общий чат администраторов.

---

## 4. Пользовательские роли

### 4.1 Студент

Пользователь, который обращается к боту через VK.

Функции:

- выбор отдела;
- заполнение анкеты заявки;
- просмотр статуса своих заявок;
- подписка на анонсы;
- регистрация на мероприятия;
- просмотр FAQ и получение готовых ответов.

### 4.2 Администратор отдела

Сотрудник, который обрабатывает заявки по своему отделу.

Функции:

- просмотр новых заявок;
- открытие карточки заявки;
- ответ студенту;
- смена статуса;
- просмотр истории;
- массовый ответ по нескольким заявкам;
- рассылка анонсов для Культмасс.

### 4.3 Суперадмин

Полный доступ ко всей системе.

Функции:

- управление администраторами;
- управление базой знаний;
- просмотр всех заявок;
- просмотр логов;
- настройка email-отчётов;
- экспорт сводок в Excel;
- мониторинг KPI и статусов.

---

## 5. Структура отделов и сценарии

## 5.1 Жилбыт

### Назначение

Полноценная система заявок по проблемам в общежитии.

### Пользовательский сценарий

1. Бот запрашивает ФИО.
2. Запрашивает номер общежития.
3. Запрашивает тему обращения.
4. Запрашивает подробное описание проблемы.
5. Текст проходит проверку по базе знаний по полям `keywords`.
6. Если найдено совпадение — заявка закрывается автоматически со статусом `Выполнено (авто)`.
7. Если совпадений нет — создаётся заявка со статусом `В обработке`.

### Статусная цепочка

- `Новое`
- `В обработке`
- `Передано в администрацию СГ`
- `Передано в Хозчасть`
- `Выполнено`
- `Выполнено (авто)`

### Администраторский сценарий

- просмотр новых заявок;
- смена статуса;
- ответ студенту;
- при необходимости массовый ответ.

---

## 5.2 Культмасс

### Назначение

Обработка заявок и взаимодействие со студентами по мероприятиям и предложениям.

### Пользовательские сценарии

#### Анонсы

- подписка/отписка от рассылки;
- получение новых объявлений от администратора.

#### Регистрация на мероприятие

- бот показывает список активных мероприятий;
- студент выбирает мероприятие;
- подтверждает регистрацию;
- данные сохраняются в таблицу `registrations`.

#### Предложение / идея

- анкета: ФИО, тема, описание;
- заявка создаётся в отдел Культмасс;
- статус `Новое`;
- администратор отвечает вручную.

---

## 5.3 Информ

### Назначение

Интерактивное FAQ-дерево без создания заявки, с возможностью эскалации.

### Пользовательский сценарий

- бот показывает корневой вопрос;
- студент выбирает вариант ответа;
- бот переходит по дереву до конечного ответа;
- на любом шаге студент может выбрать «Связаться с администратором»;
- создаётся заявка на отдел `Информ` без анкеты проживания.

### Требования к данным

- единая база знаний по отделу;
- отдельная структура `faq_nodes` для дерева вопросов.

---

## 5.4 Корпоративный

### Назначение

Упрощённый приём обращений без автоответов и длинных статусных цепочек.

### Пользовательский сценарий

1. Водится ФИО.
2. Водится общежитие.
3. Вводится тема.
4. Водится описание.
5. Заявка создаётся со статусом `Новое`.
6. Администратор отдела отвечает и закрывает.

---

## 5.5 Анонимное обращение

### Назначение

Отдельный вход для анонимного обращения.

### Пользовательский сценарий

- студент выбирает «Анонимное обращение»;
- бот запрашивает только текст;
- заявка создаётся как анонимная;
- `user_id = NULL`;
- `department_id = NULL`;
- статус = `Анонимное`;
- обращение доступно только суперадмину.

---

## 6. Главное меню и навигация

Для студента после команды `/start` бот должен показывать клавиатуру:

- `Жилбыт`
- `Культмасс`
- `Информ`
- `Корпоративный`
- `Анонимное обращение`
- `Мои заявки` — только если есть активные заявки

---

## 7. Требования к администраторскому интерфейсу

После авторизации через привязку `VK ID` к учётке суперадмина администратор отдела должен видеть меню:

### 7.1 Новые заявки

Список необработанных заявок.

При выборе заявки открывается карточка:

- ФИО;
- общежитие;
- тема;
- описание;
- статус;
- кнопки:
  - `Ответить`;
  - `Сменить статус`;
  - `Массовый ответ`.

### 7.2 История заявок

Фильтрация:

- по статусу;
- по дате;
- по поиску по тексту/теме.

### 7.3 Рассылка

Только для отдела `Культмасс`.

- отправка анонсов всем подписчикам;
- инициатором является администратор.

---

## 8. Веб-панель суперадмина

### Требования

Защищённая админ-панель с формой логина/пароля.

### Блоки функциональности

#### 8.1 Управление администраторами

- добавление/удаление администраторов;
- привязка к отделу;
- назначение роли: `admin` / `superadmin`.

#### 8.2 База знаний

- `Жилбыт`, `Корпоративный`, `Культмасс` — таблица пар: `keywords` → `answer`;
- `Информ` — конструктор FAQ-дерева.

#### 8.3 Просмотр всех заявок

- фильтры;
- сортировка;
- экспорт/просмотр карточки.

#### 8.4 Логи действий

- кто совершил действие;
- когда;
- что именно было сделано.

#### 8.5 Настройка email-отчётов

- один общий email;
- один email на отдел;
- список адресов хранится в настройках.

#### 8.6 Отчётность и мониторинг

- статистика по отделам;
- процент выполнения;
- количество заявок в работе;
- ручной экспорт в Excel за произвольный период.

---

## 9. Данные и модели

### 9.1 База данных

Использовать PostgreSQL.

### 9.2 Минимальный набор таблиц

```sql
users: id, vk_id, full_name, dormitory, created_at

departments: id, name

admins: id, user_id, department_id, role

tickets: id, user_id (nullable), department_id, topic, description,
         status, response_text, is_anonymous (bool),
         auto_closed (bool), created_at, updated_at

knowledge_base: id, department_id, keywords (text), answer (text)

faq_nodes: id, department_id, parent_id (nullable), question (text),
           is_final (bool), final_answer (text), button_text (text),
           order_index (int)

subscriptions: user_id, department_id

events: id, department_id, title, description, event_date, created_at

registrations: id, user_id, event_id, registered_at

logs: id, user_id, action, details, created_at
```

### 9.3 Правила хранения

- пользователь идентифицируется по `vk_id`;
- если обращение анонимное, `user_id` должен быть `NULL`;
- для отдела `Информ` отдельно хранится FAQ-дерево;
- для `Культмасс` хранится список мероприятий и регистраций.

## 10. Отчётность

### 10.1 Ежедневный отчёт

Ежедневно в 09:00 система должна создавать Excel-файл за предыдущий день.

### 10.2 Содержимое файла

#### Лист 1: Сводка

- новые заявки по отделам;
- закрытые заявки;
- авто-закрытые заявки;
- процент выполнения.

#### Лист 2: Детализация

- `ID`;
- ФИО;
- общежитие;
- отдел;
- тема;
- описание;
- статус;
- ответ;
- маркер `авто/ручной`.

#### Лист 3: Анонимные обращения

Отдельный блок с анонимными заявками.

### 10.3 Формула процента выполнения

$$
\text{Процент выполнения} = \frac{\text{количество выполненных заявок за день}}{\text{общее количество заявок за день}} \times 100\%
$$

Формула считается отдельно по каждому отделу и в целом.

### 10.4 Рассылка

Отправка файла на все email-адреса, указанные суперадмином.

## 14. Критерии приёмки MVP

Система считается готовой для MVP, если:

- студент может выбрать раздел и пройти базовый сценарий;
- заявка создаётся и сохраняется в БД;
- админ может открыть заявку, ответить и сменить статус;
- студент видит историю своих заявок;
- анонимное обращение попадает в общий список суперадмина;
- ежедневный отчёт формируется и отправляется по email;
- VK-бот работает через общую бизнес-логику.

---

## 15. Ограничения и риски

### Ограничения

- на MVP веб-панель должна быть простой серверной отрисовкой без сложного SPA;
- FAQ-дерево реализуется после базового рабочего потока;
- подписки и мероприятия для Культмасс не должны зависеть от внешних ссылок.

### Риски

- несогласованность статусов между отделами;
- отсутствие единых правил для анонимных обращений;
- особенности UX в VK;
- отсутствие чёткой схемы прав доступа у администратора.

---

## 16. Рекомендации по реализации

1. Сначала реализовать модель данных и миграции.
2. Затем перенести в ядро все общие методы.
3. После этого отдельно подключать отделы по приоритету.
4. Веб-панель построить как отдельный слой поверх общей БД.
5. Отчётность вынести в отдельный фоновой планировщик, чтобы не блокировать основной ботовый цикл.

---

## 17. Итог

Проект представляет собой многоотдельностную систему студенческой поддержки, где основной акцент — единая логика заявок, отделённая от интерфейса платформы. В рамках MVP приоритетом являются база данных, поток заявок, админ-обработка и отчётность, а FAQ-дерево и дополнительные функции могут быть вынесены в следующие итерации.
