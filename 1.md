## Сильные стороны

### 1. Нормально выбран базовый стек

Python 3.11, VKBottle, PostgreSQL, SQLAlchemy Async, Alembic и Docker — разумный набор для постоянно работающего VK-бота. Структура разделена на `core`, `bots/vk`, миграции и инфраструктуру, поэтому проект можно развивать без полного переписывания. 

### 2. Есть хорошая заготовка модели данных

В моделях уже предусмотрены:

- пользователи и VK ID;
- администраторы и роли;
- отделы;
- заявки;
- база знаний;
- FAQ-дерево;
- подписки;
- мероприятия и регистрации;
- журнал действий.

Это хороший фундамент под заявленное ТЗ. Особенно полезны внешние ключи, уникальность `vk_id` и уникальность подписки пользователя на отдел. 

### 3. Миграция БД уже есть

В отличие от некоторых утверждений в `True.md`, в текущем репозитории присутствует полноценная начальная Alembic-миграция. Это правильнее, чем создавать таблицы через `Base.metadata.create_all()` при каждом старте. 

### 4. Есть базовая эксплуатационная упаковка

Плюсы Docker-конфигурации:

- PostgreSQL вынесен в отдельный сервис;
- данные сохраняются в named volume;
- секреты передаются через `.env`;
- контейнер приложения запускается не от root;
- включён `restart: unless-stopped`.

Для небольшого VPS это вполне практичная стартовая схема. 

### 5. Отчётность реализована лучше, чем описано в ТЗ

В `core/reporting.py` уже есть:

- Excel с листом сводки;
- детализация заявок;
- отдельный лист анонимных обращений;
- отправка в VK;
- SMTP-рассылка;
- ежедневный asyncio-планировщик.

Это наиболее законченная часть проекта. 

### 6. Документация для запуска достаточно полезная

README описывает Docker-запуск, локальный запуск, переменные окружения, резервное копирование и работу на VPS. Также отдельно объясняется, почему VK Long Poll требует постоянно работающего процесса. Для начинающего владельца проекта это хороший плюс. 

## Слабые стороны и риски

### P0 — главный блокер: бизнес-функции отсутствуют

Все основные разделы сейчас являются заглушками:

- «Жилбыт» не создаёт заявку;
- «Культмасс» не показывает события и не регистрирует студентов;
- «Информ» не использует FAQ;
- «Корпоративный» не принимает обращения;
- анонимная форма не реализована;
- «Мои заявки» всегда отвечает, что активных заявок нет;
- администратор не может открыть, обработать или закрыть заявку.

Это честно отражено в README и ТЗ, но фактически означает, что бот пока выполняет роль демонстрационного меню, а не полноценного продукта. 

### P0 — несогласованная модель прав доступа

В `start_handler` администратор определяется через `BotCore.is_admin(user)`, где учитывается таблица `admins`. Но обработчики админ-панели и отчётов проверяют только `ADMIN_VK_IDS` из `.env`.

Из-за этого возможен сценарий:

1. администратор добавлен в таблицу `admins`;
2. он видит кнопку отчёта;
3. нажимает её;
4. получает отказ, потому что его VK ID не указан в `ADMIN_VK_IDS`.

Кроме того, кнопка «Админ-панель» фактически не добавляется в клавиатуру. Должен быть единый метод авторизации, например `require_admin()` с проверкой роли и отдела. 

### P0 — анонимность не защищена на уровне отчётности

Модель заявки позволяет связать анонимную заявку с `user_id`, а детализация отчёта для всех заявок выводит:

- ФИО;
- общежитие;
- описание;
- ответ;
- статус.

Если будущая анонимная форма будет сохранять пользователя для технической связи, его личные данные попадут в общий лист «Детализация». Отдельный лист «Анонимные обращения» эту проблему не устраняет.

Нужно явно определить политику:

- для анонимной заявки `user_id` должен быть `NULL`, либо;
- в отчётах ФИО и общежитие должны маскироваться;
- доступ к анонимным данным должен быть только у суперадмина.

Это критично, потому что бот работает с потенциально чувствительными обращениями студентов. 

### P1 — нет тестов и проверок качества

В репозитории нет unit-тестов, интеграционных тестов, линтера, форматтера или type-checking. В GitHub Actions обнаружен только workflow Dependency Graph, а не запуск тестов или проверка сборки. 

Для проекта с БД, VK API, ролями и фоновой рассылкой это высокий риск. Минимальный набор тестов должен покрывать:

- создание пользователя;
- проверку ролей;
- создание анонимной заявки;
- переходы статусов;
- фильтрацию «Мои заявки»;
- генерацию Excel;
- отсутствие ФИО в анонимном отчёте;
- повторную регистрацию на мероприятие.

### P1 — зависимости невоспроизводимы

В `requirements.txt` почти нет фиксированных версий:

```text
python-dotenv
vkbottle
aiohttp
openpyxl
SQLAlchemy>=2.0
asyncpg
alembic
```

Сегодня контейнер может собраться, а через несколько месяцев — получить несовместимую версию зависимости. Лучше зафиксировать версии через `requirements.lock`, `pip-tools` или хотя бы указать проверенные диапазоны. 

### P1 — проблемы со временем и часовыми поясами

Планировщик использует `datetime.now()` и наивные `datetime` без timezone. В Docker-контейнере часовой пояс обычно UTC, поэтому настройка:

```env
REPORT_TIME=09:00
```

может означать 09:00 UTC, а не 09:00 по Москве.

Та же проблема касается выборки заявок за день: отчёт может взять границы суток не в том часовом поясе, который ожидает владелец проекта.

Нужно:

- выбрать timezone проекта, например `Europe/Moscow`;
- использовать timezone-aware даты;
- хранить даты в UTC;
- переводить их в локальную зону только при отображении и формировании отчёта.

### P1 — ошибка VK блокирует email-рассылку

В `_report_loop` сначала выполняется отправка в VK, затем email. Обе операции находятся внутри одного `try`. Если VK временно недоступен, до email-кода выполнение не дойдёт.

Лучше разделить каналы:

```python
try:
    await send_report_to_vk(...)
except Exception:
    logger.exception("VK report failed")

try:
    await asyncio.to_thread(send_report_email, ...)
except Exception:
    logger.exception("Email report failed")
```

Тогда сбой одного канала не уничтожит второй.

### P1 — потенциальная проблема при повторном запуске polling

`vk_bot.on_startup.append(_start_scheduler())` добавляется внутри цикла повторного запуска. Сам формат добавления coroutine для VKBottle допустим, но при остановке polling и повторной попытке в список могут добавляться новые startup-задачи.

Стоит зарегистрировать scheduler один раз до цикла либо хранить созданную задачу и не запускать вторую копию. Иначе после сетевого сбоя возможны дублирование отчётов и несколько фоновых циклов.

### P1 — слабая готовность к конкурентным запросам

`get_or_create_user()` сначала делает `SELECT`, потом `INSERT`. Если два сообщения от одного нового пользователя придут одновременно, оба процесса могут не найти пользователя и столкнуться с ошибкой уникальности `vk_id`.

Надёжнее использовать PostgreSQL upsert или обработку `IntegrityError`.

### P2 — схема БД требует усиления

В текущей миграции некоторые поля, которые в ORM имеют Python-дефолты, остаются nullable в самой БД:

- `Ticket.status`;
- `Ticket.is_anonymous`;
- `Ticket.auto_closed`;
- `Admin.role`.

Также стоит добавить:

- уникальность `(user_id, event_id)` для регистраций;
- индексы по `tickets.user_id`, `tickets.department_id`, `tickets.status`, `tickets.created_at`;
- явные `ondelete` для внешних ключей;
- ограничения согласованности FAQ, например обязательный `final_answer` для финального узла.

Пока данных мало, это не чувствуется, но при росте проекта начнутся проблемы с целостностью и производительностью.

### P2 — нет защиты от спама и аудита действий

Модель `Log` уже создана, но фактического логирования пользовательских и административных действий нет. Также отсутствуют:

- rate limiting;
- защита от массовых сообщений;
- журнал смены статусов;
- журнал доступа к анонимным обращениям;
- понятное разделение прав по отделам.

Для студенческого бота это не обязательно в первом прототипе, но нужно заложить до публичного запуска.

### P2 — инфраструктура годится для MVP, но не для серьёзной эксплуатации

`docker-compose.yml` не содержит healthcheck для PostgreSQL. `depends_on` гарантирует порядок запуска контейнеров, но не готовность базы принимать подключения.

Также приложение само пытается подключаться к системной БД `postgres` и создавать целевую базу. В Docker это работает при стандартных правах PostgreSQL, но на managed PostgreSQL пользователь приложения часто не имеет права `CREATE DATABASE`.

Лучше:

- создавать БД инфраструктурой;
- в приложении выполнять только миграции;
- добавить healthcheck;
- разделить deployment-команды и runtime-команды.

## Отдельная проблема документации

Документация противоречит сама себе:

- README уже заявляет реализованную отчётность;
- текущий код действительно содержит отчётность;
- раздел анализа в `TECHNICAL_SPEC.md` всё ещё говорит, что отчётность не реализована;
- `True.md` утверждает, что Alembic и email-рассылки отсутствуют, хотя в текущем дереве они есть.

`True.md` лучше удалить или заменить на актуальный changelog/status-файл. Иначе через несколько итераций будет непонятно, чему доверять: коду, ТЗ или старому аудиту. 

## Что делать в первую очередь

1. Реализовать рабочий сценарий «Жилбыт»: форма → заявка в БД → уведомление администратору → ответ → смена статуса.
2. Привести все проверки ролей к одному механизму.
3. Зафиксировать правила анонимности и исправить Excel-отчёт.
4. Добавить тесты для `BotCore`, заявок, прав и отчётности.
5. Исправить timezone и разделить ошибки VK/email.
6. Зафиксировать версии зависимостей и добавить CI.
7. После этого подключать FAQ, мероприятия, подписки и веб-панель.

**Вердикт:** архитектурно проект начат правильно, а Docker, миграции и отчётность дают хорошую основу. Но выпускать его как рабочий бот сейчас нельзя: отсутствует основной поток заявок, права доступа противоречивы, анонимность не гарантирована, автоматические проверки качества отсутствуют.
